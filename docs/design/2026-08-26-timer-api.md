# Timer API design

**Date:** 2026-08-26
**Status:** Accepted — not yet implemented. Blocked on [c-next#1207](https://github.com/jlaustill/c-next/pull/1207)'s remainder.

## Context

The committed implementation is a proof of concept: it exists to prove the idea works, and
it does — 23 tests pass against a hand-driven clock. Nothing consumes the library yet, so
the API can still change freely, and this is the moment to settle it.

The design goal is narrow and it drives every decision below: **a timer declaration should
be complete on its own.** No constructor, no `setup()` step, no periodic service call. If a
user can forget it, the library should not need it.

## What changes

| | Proof of concept | This design |
| --- | --- | --- |
| Type name | `ElapsedTime.Config` | `ElapsedTime.Timer` |
| Declaration | 5 fields, 2 of them internal state | 2 fields |
| Reading elapsed time | `timeSince()` (u32) and `value()` (u64) | `elapsed()` (u64) |
| Overflow handling | `handleOverflow()`, public, caller must remember | private, automatic |
| Fold threshold | `rollOverAt` field on every timer | fixed 2^31, internal |
| First use | fires immediately with a garbage origin | seeds itself, fires one interval later |
| Setting the origin | `seed()` and `reset()` | `resetTo()` and `reset()` |
| Time until due | — | `remaining()` |
| Long one-shots | — | `hasElapsed()` |
| `tickSource` in C | global symbol | `ElapsedTime__tickSource` |

## The API

```cnx
scope ElapsedTime {
    public u32 tickSource() { return 0; }

    public struct Timer {
        u32 dueEvery;        // isDue interval; 0 = never due
        tickSource tick;     // the clock
        u64 total;           // internal -- folded elapsed
        u32 startedAtTick;   // internal -- origin of the current interval
        bool started;        // internal -- false until first touch
    }

    public bool isDue(Timer timer);                  // due? advance and say true
    public u64  elapsed(Timer timer);                // total elapsed, unbounded
    public bool hasElapsed(Timer timer, u32 ticks);  // non-advancing threshold test
    public u32  remaining(Timer timer);              // ticks until due
    public void reset(Timer timer);                  // origin <- tick()
    public void resetTo(Timer timer, u32 now);       // origin <- now
}
```

```cnx
ElapsedTime.Timer elapsed250 <- { dueEvery: 250, tick: millis };
```

That declaration is the whole setup. The struct is also **smaller** than the proof of
concept's: `started` adds a byte, deleting `rollOverAt` removes four.

Field order is deliberate — the two fields a user writes come first, so the struct reads in
the order it is typed.

## Decisions

### Partial initializers need no language change

`{ dueEvery: 250, tick: millis }` transpiles today. C-Next emits a designated initializer
and C99 6.7.9p21 zero-fills every omitted member, verified by compiling and running:
`total=0 startedAtTick=0 dueEvery=250 tick=myClock`. The internal fields never appear at a
call site because a user never has to write them, not because the language hides them.

### Folding is automatic and private

The proof of concept required the caller to run `handleOverflow()` periodically to push past
the 49.7-day ceiling. That is a step a user can forget, and forgetting it is silent.

Folding is now private and called from the accessors. The threshold is a fixed **2^31**:

| Threshold | Margin at ms | Margin at us | Cost |
| --- | --- | --- | --- |
| `u32max - 10000` | 10 s | **10 ms** | unsafe: a 10 ms gap between calls loses 2^32 ticks |
| **2^31** | **24.8 days** | **35.8 min** | one u64 add per 2^31 ticks |
| 0 (fold always) | 49.7 days | 71.6 min | a u64 add on every call |

2^31 is also the cheapest threshold to test: `since >= 0x80000000` is "is bit 31 set", a
single high-byte test on AVR rather than a four-byte comparison.

`rollOverAt` is deleted rather than renamed. Once folding is internal, a user has no reason
to tune how often it happens, and the field was only ever there to skip the 64-bit add.

### `timeSince` and `value` collapse into `elapsed`

Once folding is private, "ticks since the last fold" is not a quantity a user can observe,
so it should not be a function they can call. There is one question — how much time has
passed since this timer started — and `elapsed()` answers it, in u64, unbounded.

The cost is that every accessor mutates (folding is a write), so none can take `const`. That
is honest: a timer is a stateful object, and `elapsedMillis` behaves the same way.

### `hasElapsed` runs on the u64

`hasElapsed(timer, ticks)` tests total elapsed against a threshold without advancing the
timer. It serves one-shots that have no `dueEvery` — "has it been five seconds since boot?"

It is **not** a cheap u32 path. "Elapsed since reset" is `total + since`, inherently u64.
The justification is reach, not speed:

| Tick | u32 ceiling | u64 ceiling |
| --- | --- | --- |
| milliseconds | 49.7 days | 584,542,046 years |
| microseconds | 71.6 minutes | 584,542 years |
| nanoseconds | 4.3 seconds | 585 years |

A threshold of one year is a legitimate call on hardware that will never reach its own
ceiling.

### `remaining` returns u32max when never due

`remaining()` reports ticks until the next firing: 0 when overdue, and **`u32max` when
`dueEvery` is 0**. The use case is low-power scheduling, where a caller takes the *minimum*
across several timers to decide how long it may sleep. `u32max` is the identity for minimum,
so a never-due timer correctly does not constrain the sleep. Returning 0 would make every
never-due timer prevent sleeping entirely.

### `seed` is dropped in favor of `resetTo`

`reset(timer)` and `resetTo(timer, now)` are one pair that teach each other: `resetTo` is
built from `reset`, which a reader has already met. `seed` was a third word, borrowed from
RNG jargon, for a concept already covered. Seeding several timers from one clock reading
still aligns them exactly — that is `resetTo`.

### Lazy seeding via `started`

C-Next has no constructors (ADR-005), and a global's initializer must be a compile-time
constant, so a timer cannot capture its clock where it is declared. A timer left at
`startedAtTick: 0` while `millis()` already reads 40,000 fires immediately on first use, and
`elapsed()` reports 40 seconds that never elapsed.

`started` is false until the first touch. Every public function routes through `sinceNow()`,
which seeds the origin from the clock and reports not-yet. First firing lands one full
interval later.

Builders were considered and rejected. A builder works for a local
(`Timer t <- ElapsedTime.createTimer(250, millis);` compiles and runs, capturing the clock
correctly), but **not for a global** — the generated C is
`ElapsedTime__Timer t = ElapsedTime__createTimer(250U, millis);` at file scope, which fails
with `initializer element is not constant`. That is [c-next#1202](https://github.com/jlaustill/c-next/issues/1202),
and fixing it will not help: #1202's fix is a diagnostic, while the underlying rule is C's
own requirement that static storage duration means a constant initializer. Most embedded
timers are globals, so the builder cannot be the primary mechanism. The `started` flag is
one mechanism that covers globals and locals alike.

## Internal structure

Three private functions, each the single owner of one decision:

| Private | Owns | Called by |
| --- | --- | --- |
| `sinceTick(base, now)` | the wrap branch | `sinceNow` |
| `sinceNow(timer, now)` | lazy seeding, and returning `since` | every public function |
| `valueAt(timer, now)` | the u64 cumulative and the 2^31 safety fold | `elapsed`, `hasElapsed` |

**Every public function reads `tick()` exactly once** and passes that `now` down. Reading
once for the difference and again for a new origin loses whatever elapsed in between — a few
ticks per call, forever. This discipline held in the proof of concept and matters more now
that more functions mutate.

Seeding lives only in `sinceNow`, so `isDue` and `elapsed` cannot disagree about what a
fresh timer means. On first touch: `elapsed` returns 0, `isDue` returns false, `remaining`
returns `dueEvery`.

### `isDue` deliberately omits the safety fold

`isDue` folds on every firing, so a working periodic timer folds constantly and never
approaches 2^31. Adding the safety fold there would buy nothing and would *break* long
intervals: `since` would cross 2^31 and fold to zero while still short of `dueEvery`, and
the timer would never fire at all.

This asymmetry is intentional and must be commented in the source, so that a later reader
does not "unify" the two paths.

### Preserved from the proof of concept

- Elapsed time is computed, never stored — a timer cannot go stale.
- The wrap is one visible branch, because C-Next clamps rather than wraps.
- `isDue` advances *before* returning true, so a handler's duration cannot push the cadence.
- It advances *to now*, not by one interval, so a long stall fires once rather than once per
  missed slot.
- `dueEvery: 0` means never due, not always due.

## Constraint

**`dueEvery` must stay below 2^31** — 24.8 days at milliseconds. Above that the safety fold
and the due check fight, per the section above. `hasElapsed` is the right tool for longer
intervals: it runs on the u64 and tops out 584 million years away.

## Dependency on C-Next

`tickSource` moves inside the scope so nothing lands in the global C namespace unprefixed.
The bare reference this design uses does not currently compile. Reduced matrix, every row
transpiled against `main` and compiled with `gcc -std=c99`:

| function defined | struct | reference | typedef emitted | gcc |
| --- | --- | --- | --- | --- |
| global | global | bare | `tickSource_fp` | pass |
| global, either order | scope-nested | bare | `tickSource_fp` | pass |
| **scope-local, either order** | **scope-nested** | **bare** | **none** | **fail** |
| scope-local | scope-nested | `this.tickSource` | `Probe__tickSource_fp` | pass |
| scope-local | global | `Probe.tickSource` | `Probe__tickSource_fp` | pass |

Declaration order is not the trigger; a bare reference to a scope-local function-as-type is.
This is [#1207](https://github.com/jlaustill/c-next/pull/1207)'s "What is not fixed" item 2,
[commented with this matrix](https://github.com/jlaustill/c-next/pull/1207#issuecomment-5432193630),
and fixed in [c-next#1281](https://github.com/jlaustill/c-next/pull/1281) -- which also
corrects the ADR-057 rule that caused it: functions were omitted from the type-kind sets when
the type side was written, so a scope function was invisible at type positions.

`this.tickSource` compiles today and is legitimate C-Next. This library will still wait for
the bare reference and contribute the fix upstream, rather than ship a spelling chosen to
route around a defect.

## Verified during design

Every claim above that could be tested, was:

- partial initializers zero-fill omitted members — compiled and run
- the scope-local bare reference fails, and `this.`/qualified forms succeed — 8-case matrix
- declaration order is not the discriminator — global-after-struct compiles clean
- a builder works for a local and produces the right origin — ran, `startedAtTick=12345`
- a builder fails for a global — `initializer element is not constant`

Not verified, and recorded as a hypothesis only: that the bare-name type qualification
predicate omits ADR-029 callback names, which would explain why the `.c` resolves the call
correctly while the `.h` does not resolve the type.

## Incidental findings

All filed upstream. Designing this library was the exercise that surfaced them.

- [c-next#1277](https://github.com/jlaustill/c-next/issues/1277) -- `return { ... }` from a
  function with a struct return type fails with "Cannot infer struct type - no explicit type
  and no context". An explicit typed local works.
- [c-next#1278](https://github.com/jlaustill/c-next/issues/1278) -- the self-scope rule is
  enforced at parameter type positions but not struct field positions, so `Probe.tickSource`
  inside `scope Probe` is accepted where the parameter form is correctly rejected.
- [c-next#1279](https://github.com/jlaustill/c-next/issues/1279) -- a scope-local
  function-as-type used as a *parameter* in its own scope fails with E0422.
- [c-next#1280](https://github.com/jlaustill/c-next/issues/1280) -- a global variable of a
  function-as-type is accepted and emits uncompilable C; it should be rejected.

The last one clarified a rule this design depends on: a function-as-type is a type reference
for **passing**, never a way to create storage. It is valid as a parameter and as a struct
field -- which is what `tickSource tick` is here -- and invalid as a standalone variable or a
scope member. ADR-029 now records it.
